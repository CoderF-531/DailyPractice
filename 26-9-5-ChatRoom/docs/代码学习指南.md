# 终端 UDP 聊天室代码学习指南

这是一份给第一次接触网络编程和多线程 C++ 的阅读路线。不要一开始就从 `server/main.cpp` 第一行读到最后一行；先建立整体模型，再逐层看实现。

## 1. 先记住这张图

```text
用户输入
   │
   ▼
客户端 main.cpp ── serializeMessage ── sendto ── UDP 网络
                                             │
                                             ▼
服务端 recvfrom ── DatagramHandler 回调 ── ThreadPool
                                             │
                                             ▼
                                      parseMessage
                                             │
                                             ▼
                                      聊天室业务
                                             │
                              sendSystem / sendTo 广播
                                             │
                                             ▼
客户端接收线程 ── recvfrom ── 回调 ── parseMessage ── 终端输出
```

程序分成三层：

1. **公共基础层**：协议、Socket、线程池、日志，不关心“谁加入了聊天室”。
2. **业务层**：服务端维护在线用户并广播，客户端读取输入并显示消息。
3. **程序入口层**：解析命令行参数、启动对象、处理退出。

## 2. 第一步：先跑起来

在 Linux 虚拟机中：

```bash
cd ~/DailyPractice/26-9-5-ChatRoom
make
make test
./bin/chat_server
```

再打开两个终端窗口，分别运行：

```bash
./bin/chat_client 127.0.0.1 alice
./bin/chat_client 127.0.0.1 bob
```

在 `alice` 中输入一行文字，`bob` 会收到；输入 `/quit` 退出。当前服务端只把聊天消息发送给“其他客户端”，因此发送者不会看到自己的消息，这是代码中 `handleChat` 的明确选择。

### 命令行参数

```text
chat_server [port]
chat_client <server_ip> <nickname> [port]
```

- 服务端绑定 `0.0.0.0`，表示监听本机所有 IPv4 网卡，不需要输入服务端 IP。
- 客户端必须知道服务端 IP。同机测试使用 `127.0.0.1`，跨机器测试使用服务端所在机器的局域网 IP。
- 端口默认是 `9000`。客户端的本地端口不需要指定，程序通过 `bindAny(0)` 让操作系统分配临时端口。

## 3. 第二步：认识 Makefile

打开 [Makefile](../Makefile)，只看几个核心变量和目标：

```make
COMMON_SOURCES := $(wildcard src/common/*.cpp)
SERVER_SOURCES := $(COMMON_SOURCES) $(wildcard src/server/*.cpp)
CLIENT_SOURCES := $(COMMON_SOURCES) $(wildcard src/client/*.cpp)
```

这表示服务端和客户端都会编译公共代码，但各自只额外编译自己的入口文件。

```make
$(BUILD_DIR)/%.o: %.cpp
    $(CXX) $(CXXFLAGS) -c $< -o $@
```

这是“源码 `.cpp` 编译成目标文件 `.o`”的通用规则。`$<` 是当前源文件，`$@` 是目标文件。

```make
all: server client
test: $(BIN_DIR)/protocol_test
```

常用目标：

- `make`：构建客户端和服务端。
- `make test`：构建并运行协议测试。
- `make clean`：删除 `build/` 和 `bin/` 生成物。

建议第一次学习时运行 `make -n all`，它只打印命令不执行，可以看清编译和链接顺序。

## 4. 第三步：从协议模块开始

阅读顺序：

1. [include/chat/protocol.h](../include/chat/protocol.h)
2. [src/common/protocol.cpp](../src/common/protocol.cpp)
3. [tests/protocol_test.cpp](../tests/protocol_test.cpp)

### 4.1 数据结构

```cpp
enum class MessageType { Join, Chat, Leave, System };

struct Message {
    MessageType type;
    std::string nickname;
    std::string content;
};
```

`Message` 是程序内部使用的结构体；网络上传输的不是结构体，而是文本：

```text
CHAT|alice|hello
```

这样做的好处是可以直接用终端工具观察报文，也不依赖 C++ 结构体的内存布局。

### 4.2 序列化和解析

- `serializeMessage`：`Message` 转成字符串，准备交给 `sendto`。
- `parseMessage`：收到字符串后，检查长度、字段、消息类型和内容，再转成 `Message`。
- `std::optional<Message>`：解析成功返回消息；失败返回空值。它比返回一个“可能无效的 Message”更明确。
- `std::string_view`：只读地查看字符串，不负责拥有字符串内存；异步保存数据时必须复制成 `std::string`。

重点看 `parseMessage` 的校验顺序：先判断整体长度，再找分隔符，最后检查昵称和内容。网络数据是不可信输入，不能未经校验就使用。

### 4.3 你可以做的实验

在协议测试中依次加入这些报文，观察测试结果：

```text
CHAT|alice|hello       # 合法
UNKNOWN|alice|hello    # 未知类型
CHAT|alice|            # 空聊天内容
JOIN|alice|unexpected  # JOIN 不允许内容
CHAT|alice|a|b         # 分隔符会破坏字段格式
```

## 5. 第四步：理解 UDP Socket 封装

阅读顺序：

1. [include/chat/udp_socket.h](../include/chat/udp_socket.h)
2. [src/common/udp_socket.cpp](../src/common/udp_socket.cpp)

### 5.1 Socket 的四个关键动作

服务端启动时的核心调用链：

```text
bindAny(9000)
  ├─ socket(AF_INET, SOCK_DGRAM, 0)
  ├─ sockaddr_in 填入 IPv4、0.0.0.0、端口
  └─ bind()
```

- `AF_INET`：使用 IPv4。
- `SOCK_DGRAM`：使用 UDP 数据报。
- `INADDR_ANY`：绑定本机所有 IPv4 地址。
- `htons`：把主机字节序的端口转为网络字节序。

收发动作：

- `recvfrom`：从任意客户端收到一个完整 UDP 数据报，同时拿到对方地址。
- `sendto`：向指定的 `sockaddr_in` 发送一个完整数据报。
- UDP 没有连接建立过程，也不保证送达、顺序和去重。

### 5.2 为什么客户端也要 bind

客户端虽然不需要固定端口，但必须拥有一个本地 UDP Socket。`bindAny(0)` 中的端口 `0` 表示让内核自动分配空闲临时端口；之后 JOIN、CHAT 和接收广播都使用同一个 Socket。

### 5.3 接收循环和超时

`receiveLoop` 使用一个可复用的栈缓冲区调用 `recvfrom`。Socket 设置了一秒接收超时，因此循环可以定期检查 `running` 标志，避免退出时永久阻塞。

```cpp
std::array<char, kMaxDatagramBytes> buffer{};
recvfrom(..., buffer.data(), buffer.size(), ...);
```

下一次 `recvfrom` 会复用这块缓冲区，所以回调交付前必须构造：

```cpp
std::string(buffer.data(), bytesRead)
```

这次复制保证异步任务拥有自己的数据，不会被下一条报文覆盖。

## 6. 第五步：理解回调

头文件中的类型别名：

```cpp
using DatagramHandler = std::function<void(Datagram)>;
```

它表示“接收一个 `Datagram`，不返回结果的可调用对象”。普通函数、Lambda、函数对象都可以作为回调。

服务端注册回调：

```cpp
socket_.setDatagramHandler([this](Datagram datagram) {
    chat::ThreadPool::instance().submit([this, datagram = std::move(datagram)]() mutable {
        handleDatagram(std::move(datagram));
    });
});
```

逐层理解：

1. `[this]` 让 Lambda 能调用当前 `ChatServer` 的成员函数。
2. `receiveLoop` 收到数据后在接收线程调用这个回调。
3. 回调把拥有数据的 `datagram` 移入线程池任务。
4. 线程池工作线程稍后调用 `handleDatagram`。

因此，回调的约定是：

- 调用线程：服务端是 Socket 接收线程，客户端是客户端接收线程。
- 参数所有权：`Datagram` 按值传入，回调可以安全地移动它。
- 执行时间：回调只负责转交任务，不做耗时业务。
- 生命周期：Lambda 捕获了 `this`，所以对象销毁前必须先停止接收线程和线程池。

## 7. 第六步：理解线程池

阅读顺序：

1. [include/chat/thread_pool.h](../include/chat/thread_pool.h)
2. [src/common/thread_pool.cpp](../src/common/thread_pool.cpp)

### 7.1 为什么需要线程池

Socket 接收线程的任务是“尽快收下一条报文”。如果它直接做昵称检查、遍历用户、广播和日志，某个慢操作会阻塞后续接收。

线程池把任务放入队列，由多个工作线程处理：

```text
接收线程 ── submit(task) ──> 任务队列 ──> 工作线程执行 task()
```

### 7.2 三个同步对象

- `mutex_`：保护 `tasks_` 和 `stopping_`。
- `condition_variable taskReady_`：没有任务时让工作线程睡眠，有任务时唤醒。
- `stopping_`：通知工作线程停止接收新任务，并在队列排空后退出。

工作线程中的代码：

```cpp
taskReady_.wait(lock, [this] { return stopping_ || !tasks_.empty(); });
```

这里必须使用谓词，因为条件变量可能发生“虚假唤醒”。被唤醒后仍要重新判断：是有任务，还是正在停止。

### 7.3 单例和生命周期

`ThreadPool::instance()` 返回函数内静态对象，因此整个进程通常只有一个线程池。构造时创建工作线程，`stop()` 设置停止标志、唤醒所有线程并逐个 `join()`。

`join()` 的含义是等待线程真正结束。程序退出前不等待线程，会留下后台线程访问已销毁对象的风险。

## 8. 第七步：理解日志模块

阅读 [include/chat/logger.h](../include/chat/logger.h) 和 [src/common/logger.cpp](../src/common/logger.cpp)。

`Logger::log` 做四件事：

1. 取得当前时间。
2. 取得当前线程 ID。
3. 组装日志文本。
4. 用静态互斥锁保护 `std::cerr` 输出。

日志输出可能来自多个线程；如果不加锁，两条日志可能交错在同一行。注意日志组件只保护日志输出，不会保护聊天室用户列表。

## 9. 第八步：阅读服务端业务

阅读 [src/server/main.cpp](../src/server/main.cpp)，建议按下面顺序：

### 9.1 `main`

`main` 只做启动工作：解析端口、注册 `SIGINT/SIGTERM`、创建 `ChatServer`、调用 `start` 和 `run`。

### 9.2 `ChatServer::start`

1. `bindAny(port)` 绑定服务端 Socket。
2. 注册数据报回调。
3. 回调将数据提交给线程池。

### 9.3 `handleDatagram`

先调用 `parseMessage`。解析失败就返回 `SYSTEM` 错误；成功后根据 `MessageType` 分派到：

- `handleJoin`：检查地址和昵称，登记用户，通知其他用户。
- `handleChat`：确认发送者已上线，复制在线用户快照，然后广播聊天报文。
- `handleLeave`：删除用户，通知剩余用户。

### 9.4 为什么要复制 recipients

`clients_` 是共享数据，访问时需要锁。但 `sendto` 可能阻塞，不能持有 `clientsMutex_` 发送网络数据。因此代码在锁内复制 `ClientInfo` 到 `recipients`，释放锁后再广播。

这是并发代码中常见的模式：

```text
加锁读取共享状态 → 复制需要的数据 → 解锁 → 执行可能阻塞的操作
```

## 10. 第九步：阅读客户端业务

阅读 [src/client/main.cpp](../src/client/main.cpp)。

客户端有两个并发角色：

- 主线程：读取 `std::cin`，发送 JOIN、CHAT、LEAVE。
- 接收线程：阻塞在 `receiveLoop`，收到服务端消息后显示。

### 10.1 `start`

解析服务端 IP，绑定本地临时端口，注册接收回调，创建 `std::thread`，最后发送 JOIN。

`std::thread([this] { ... })` 启动一个新线程执行 Lambda；线程函数结束后必须 `join`，否则 `std::thread` 析构会触发程序终止。

### 10.2 `run`

主线程使用 `std::getline` 读取整行：

- `/quit`：发送 LEAVE 并退出循环。
- 空行：忽略。
- 其他内容：发送 CHAT。

输入 EOF（例如 Ctrl-D）时也会发送 LEAVE。

### 10.3 `stop`

停止顺序是：把原子标志设为 `false`，等待接收线程结束，最后关闭 Socket。`running_` 使用原子类型，是因为主线程和接收线程都会读写它，不能用普通 `bool`。

终端输出使用 `outputMutex_`，避免主线程报错提示和接收线程消息同时写入时发生数据竞争。

## 11. 最后一层：测试和调试

当前测试集中在协议模块，因为协议是客户端和服务端共享的边界。

建议按顺序做这些实验：

1. 只运行 `make test`，确认合法和非法报文解析结果。
2. 启动服务端和一个客户端，观察 JOIN 日志。
3. 启动第二个客户端，观察 JOIN 通知和 CHAT 广播。
4. 使用相同昵称启动两个客户端，观察拒绝消息。
5. 发送 `/quit`，观察其他客户端收到 LEAVE 通知。
6. 启动服务端时传入已占用端口，观察 `bind failed` 日志。
7. 用 `Ctrl-C` 停止服务端，观察线程池停止日志。

调试时优先看三类信息：

- 客户端终端：是否收到 `JOIN_OK` 或错误提示。
- 服务端日志：报文是否被解析、用户列表是否变化、发送是否失败。
- Socket 地址：服务端端口和客户端临时端口是否与预期一致。
