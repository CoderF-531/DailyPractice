# 终端 UDP 聊天室

## 1. 项目目标

在 Linux 平台使用 C++ 实现一个基于终端的 UDP 聊天室。项目以学习网络编程、并发编程和工程化组织为主要目的，提供可运行的客户端与服务端，并通过清晰的模块边界和日志记录方便理解消息从发送到接收的完整过程。

本项目是学习型练习，不实现 GUI、数据库、账号注册登录、离线消息和端到端加密等超出当前目标的功能。

## 2. 技术范围

- 平台：Linux。
- 语言标准：C++17。
- 网络通信：POSIX Socket，使用 UDP 协议。
- 并发：C++ 标准库 `std::thread`、`std::mutex`、`std::condition_variable`。
- 任务调度：自行封装的线程池，使用单例模式管理全局实例。
- 日志：自行封装日志组件，至少支持 `INFO`、`WARN`、`ERROR` 级别，并输出时间、级别和线程标识。
- 构建：Makefile，使用 `g++` 编译 C++17 代码。

除 C++ 标准库和 Linux/POSIX 系统接口外，不依赖第三方网络或日志库。

## 3. 功能需求

### 3.1 服务端

- 启动时不接收 IP 参数，固定绑定 `0.0.0.0`（`INADDR_ANY`），以监听本机所有 IPv4 网卡。
- 端口支持命令行配置，未提供时使用默认端口 `9000`。
- 接收客户端的上线、聊天、下线请求。
- 维护当前在线客户端列表，记录昵称、客户端地址、端口和最近活动时间。
- 将一名客户端的聊天消息广播给其余在线客户端。
- 客户端上线成功时先向该客户端返回确认，再向其他在线客户端发送上线提示；客户端下线时向其余在线客户端发送下线提示。
- 对格式错误、昵称冲突、超长消息和未知消息类型进行拒绝，并记录日志；服务端不得因此退出。
- 使用线程池处理收到的数据报，Socket 接收循环不承担耗时业务处理。

### 3.2 客户端

- 启动时必须通过命令行提供服务端 IP 与昵称，端口可选，未提供时使用默认端口 `9000`。
- 客户端与服务端位于同一台机器时，服务端 IP 使用 `127.0.0.1`；服务端绑定 `0.0.0.0` 时，局域网内客户端也可使用该机器的局域网 IP 连接。
- 上线成功后，终端可持续输入并发送聊天消息。
- 独立接收线程持续显示服务端广播的聊天消息和系统提示。
- 输入 `/quit` 后向服务端发送下线请求并正常退出。
- 连接失败、发送失败或收到异常数据时给出明确终端提示并写入日志。

### 3.3 基本交互

1. 客户端启动并发送上线请求。
2. 服务端校验昵称和报文，登记客户端并广播上线通知。
3. 客户端发送聊天消息。
4. 服务端在线程池任务中校验并广播消息。
5. 客户端输入 `/quit`，服务端移除该客户端并广播下线通知。

## 4. 通信协议

传输层为 UDP。应用层使用 UTF-8 文本报文，一行表示一条消息，字段用 `|` 分隔：

```text
<type>|<nickname>|<content>
```

| `type` | 方向 | 说明 |
| --- | --- | --- |
| `JOIN` | 客户端 -> 服务端 | 上线请求，`content` 为空 |
| `CHAT` | 客户端 <-> 服务端 | 聊天内容 |
| `LEAVE` | 客户端 -> 服务端 | 下线请求，`content` 为空 |
| `SYSTEM` | 服务端 -> 客户端 | 上线、下线或错误提示 |

协议约束：

- 昵称长度为 1 到 20 个 UTF-8 字节，不能包含 `|`、换行或控制字符。
- 聊天内容不能为空，最大 512 字节，不能包含换行；超出限制的报文直接拒绝。
- 服务端向客户端返回的错误采用 `SYSTEM|server|<reason>`。
- UDP 不保证送达、顺序和去重；本项目不实现可靠传输。该限制应在运行说明中明确，后续扩展可基于消息 ID 和确认机制实现。

## 5. 模块与目录约定

```text
26-9-5-ChatRoom/
├── 项目目标.md          # 项目范围、约束与验收标准
├── README.md             # 构建、运行与测试说明
├── Makefile              # 构建入口与常用目标
├── include/              # 对外头文件，按模块命名
├── src/

```

- 文件名使用小写英文和下划线，例如 `thread_pool.h`、`chat_server.cpp`。
- 公共类型和函数放入项目命名空间，避免污染全局命名空间。
- 一个 `.cpp` 文件只放一个明确职责的实现单元；不要将客户端、服务端和通用逻辑混在同一文件。
- Makefile 至少提供 `all`、`server`、`client`、`test`、`clean` 目标；构建产物统一放入 `bin/`，不提交到版本控制。

## 6. 关键实现约束

### 6.1 线程池

- 线程池采用单例模式，禁止复制和移动。
- 任务队列必须受互斥锁保护；生产者提交任务后唤醒等待线程。
- 工作线程使用条件变量等待任务，空闲时不得忙等。
- 析构或显式停止时应拒绝新任务、唤醒工作线程并完成 `join`，不得遗留后台线程。
- 对在线客户端列表的读写必须有清晰的同步策略，不能在持锁状态下进行网络发送等可能阻塞的操作。

### 6.2 网络接口与回调

- Socket 层只负责 `socket`、`bind`、`recvfrom`、`sendto` 等 UDP 收发，不直接处理聊天室的上线、下线和广播业务。
- Socket 层收到完整数据报后，通过回调将报文内容和对端地址交给上层协议模块；回调的注册、触发线程和参数所有权必须在接口注释中写清楚。
- 接收缓冲区的数据在进入线程池或回调前必须复制，禁止把下一次 `recvfrom` 会复用的缓冲区指针传给异步任务。
- 回调中不得长时间阻塞、等待用户输入或持有在线用户列表的锁；耗时业务由上层提交至线程池。
- 客户端接收回调与终端输出并发时，应通过受互斥锁保护的消息队列或统一输出锁避免文本交错。

### 6.3 注释要求

- 注释说明设计原因、前置条件、线程边界和资源所有权，不重复代码表面含义。
- 调用 `socket`、`bind`、`recvfrom`、`sendto` 时，说明关键参数、网络字节序转换、地址结构和 UDP 无连接语义。
- 使用 `std::thread`、`std::mutex`、`std::condition_variable` 时，说明线程职责、保护的数据、等待谓词及唤醒条件。
- 回调接口必须说明调用方与被调用方的职责、可能的调用线程、参数有效期及禁止执行的阻塞操作。

### 6.4 日志

- 日志组件需线程安全，避免多线程输出交错。
- 关键事件必须记录：服务端启动/停止、客户端上线/下线、报文解析失败、消息转发、Socket 错误、线程池启动/停止。
- 日志默认输出到终端；日志文件输出可作为后续扩展。

### 6.5 错误处理与资源管理

- Socket、线程和互斥量等资源由 RAII 对象管理，避免手工资源泄漏。
- 系统调用失败时保留 `errno` 信息并记录上下文。
- 接收到不可信网络数据时，必须先校验长度和字段，再访问或转换数据。
- 不使用裸 `new`/`delete` 管理对象所有权。

## 7. 运行方式

构建与运行命令在实现后维护在 `README.md` 中。预期使用方式如下：

```bash
make
./bin/chat_server
./bin/chat_server 9001
./bin/chat_client 127.0.0.1 alice
./bin/chat_client 192.168.1.10 alice 9001
```

`127.0.0.1` 仅指向当前机器。服务端与客户端在同一台机器上运行时使用它；跨机器测试时，客户端应填写服务端所在机器的局域网 IP。

## 8. 阶段计划

1. 搭建 Makefile、目录结构和最小可构建的客户端/服务端入口。
2. 完成 UDP 收发与协议编解码，并实现单客户端通信验证。
3. 实现线程池、日志组件及服务端在线用户管理。
4. 完成多客户端广播、上线/下线通知和异常报文处理。
5. 补充测试、运行说明和关键实现注释。

## 9. 验收标准

- 项目可在 Linux 环境通过 `make` 成功构建，生成独立的客户端和服务端可执行文件。
- 服务端无需输入 IP 即可启动并绑定 `0.0.0.0`；本机客户端使用 `127.0.0.1` 可正常加入聊天室。
- 两个及以上客户端能加入同一聊天室，并实时接收其他客户端发送的消息。
- 任一客户端退出后，其余客户端能收到下线通知，服务端在线列表同步更新。
- 非法报文、重复昵称和发送异常不会导致服务端崩溃。
- 线程池停止后无未退出的工作线程；并发访问在线列表与日志输出无数据竞争。
- 关键网络接口、并发接口、回调边界、同步策略和协议处理包含解释“为什么这样实现”的必要注释，而非重复代码字面含义。
